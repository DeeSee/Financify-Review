# BankAccountService.swift — Code Review

## Баги

### 1. `fetchLocalPrimaryAccount()` — сложная логика вычисления баланса уязвима к ошибкам (строки 95–193)
Метод восстанавливает баланс, последовательно применяя отложенные операции. Проблемы:

- **`continue` при ошибке `fetchCategory`** (строки 144, 152, 169): Если категория не найдена (например, ещё не скачана в локальное хранилище), операция молча пропускается. Это искажает баланс — пользователь видит неправильную сумму без уведомления.
- **`try?` скрывает ошибки** (строки 117, 128–129, 135–136, 142, 167, 171): Все ошибки декодирования payload молча игнорируются. Повреждённая операция в очереди навсегда искажает баланс.

### 2. Дублирование `parseId(from:)` (строки 247–249)
Идентичный метод есть в `TransactionsService` (строка 120). Стоит вынести в общий utility.

## Архитектурные замечания

### 3. `primaryAccount()` всегда берёт `accounts.first` (строка 40)
```swift
let accounts: [BankAccount] = try await client.request(.accountsGET, method: .get)
guard let primary = accounts.first else { ... }
```
Порядок элементов массива от сервера не гарантирован. Если у пользователя несколько счетов, «primary» будет случайным. Нет фильтрации по id или флагу `isPrimary`.

### 4. `primaryAccount()` вызывает `synchronize()` при каждом обращении (строка 36)
Каждый вызов `primaryAccount()` запускает полную синхронизацию. Если три ViewModel'а одновременно запрашивают данные, будет три попытки синхронизации (хоть и последовательных, т.к. actor).

### 5. Множество `ModelContext` в проекте
Каждый сервис создаёт свой `ModelContext(modelContainer)`. `ModelContext` не делит кеш с другими контекстами — это может привести к stale reads. Например, `TransactionsService` вставляет транзакцию, а `BankAccountService` в своём контексте её не видит.

**Рекомендация:** Использовать один shared `ModelContext` или координировать через `ModelContainer`.
