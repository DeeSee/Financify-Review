### `Financify/Domain/BankAccount.swift` (2)

- **L16**
> Табличное выравнивание оправдано для крайне редко меняющегося, но часто читающегося кода — например, стандартной библиотеки. Для "живого" кода, который находится в развивающемся проекте, такое выравнивание привносит неоправданные сложности в поддержке: будут постоянно возникать паразитные диффы в пулл-реквестах, они затрудняют чтение и увеличивают риск пропуска дефектов при ревью

- **L28**
> Здесь и в последующих файлах достаточно много усилий вложено в ручную сериализацию и десериализацию из-за необходимости в особой логике для `Decimal` и `Date`, хотя все остальные поля сериализуются стандартно. Этого можно было достичь куда меньшими усилиями, если сделать property wrapper:
>
> ```swift
> @propertyWrapper
> struct DecimalString: Codable {
>   var wrappedValue: Decimal
>
>   init(from decoder: Decoder) throws {
>     let c = try decoder.singleValueContainer()
>     let str = try decoder.decode(String.self, forKey: .name)
>     guard let value = Decimal(string: str) else {
>       throw DecodingError.dataCorruptedError(
>         forKey: .balance, in: c,
>         debugDescription: "balance должен быть строкой-числом"
>       )
>     }
>     wrappedValue = value
>   }
>
>   // same for encoding
> }
> ```
>
> ```swift
> struct Foo: Codable {
>   @DecimalString
>   var bar: Decimal
> }
> ```

### `Financify/Persistence/NetworkReachabilityService.swift` (1)

- **L46**
> `print` — не лучшее решение для логов, он подходит разве что для локальной отладки. С ростом размера приложения объем логов будет расти, и потребуется возможность фильтрации, отключения, перенаправления потока логов, что невозможно при использовании `print`. Существует стандартное API [Logger](https://developer.apple.com/documentation/os/logger), которое в использовании не сложнее, чем `print`, оно имеет очень мощные инструменты для управления потоками логов и оптимизации на уровне компилятора.

### `Financify/Scenes/Analysis/Additional Views/CategoryCellContentView.swift` (1)

- **L124**
> На мой взгляд, подобная систематизация констант, хоть и выглядит "красиво", на самом деле только затрудняет восприятие кода и его редактирование. Я рекомендую выносить в константы только те значения, которые используются в нескольких местах: это позволяет выразить связь между разными местами в коде. Если константа используется в одном месте в верстке, то более логично прописать ее magic number-ом прямо по месту, так как верстка достаточно нередко меняется, и гораздо более вероятно, что эта константа удалится вместе с кодом, чем будет где-то переиспользована. В том коде, который мы наблюдаем, достаточно несложно при удалении кода забыть удалить соответствующую константу.
