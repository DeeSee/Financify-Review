## Общее ревью проекта (как один большой PR)

## Сильные стороны
- **Ясная идея Offline‑First**: есть очередь `PendingOperation` + сервис синхронизации.
- **Хорошая модульность по слоям**: `Clients` / `Services` / `Persistence` / `Scenes` / `Domain`.
- **Демонстрация гибридного UI**: SwiftUI + UIKit (VIP/Clean Swift) как отдельный модуль.
- **Вынос кастомных компонентов в локальные пакеты** (`LaunchAnimation`, `Utilities/PieChart`).

## Главные проблемы (приоритет P0–P1)
- **Конкурентность SwiftData (P0)**:
  - `BackupService` не actor, но используется из нескольких actor’ов → риск гонок `ModelContext`.
  - `@Model` классы помечены `Sendable` → потенциально неверная гарантия и скрытые data race.
- **Offline‑sync семантика и корректность данных (P0)**:
  - `TransactionsService.updateLocalStore` удаляет все транзакции и перезаписывает → риск потери/«мерцания» офлайн данных.
  - Нет reconciliation для офлайн POST (temp id ↔ server id); `SynchronizationService` не читает ответ тела.
  - Политика “4xx = фатально удалить из очереди” слишком грубая (401/403/409/429 нельзя просто выкидывать).
- **Парсинг Decimal зависит от локали (P0)**:
  - В доменных моделях/DTO часто используется `Decimal(string:)` без `locale:`. На локалях с запятой строки вида `"1234.56"` приводят к **потере дробной части**.
- **Обработка ошибок и логирование (P1)**:
  - Много `print`, иногда `fatalError`. Нет единого UX для ошибок (алерт/баннер/ретраи).
  - В `NetworkClient` тело ошибки почти всегда не пробрасывается, поэтому диагностика слабая.
- **Тесты не соответствуют реальной сериализации (P1)**:
  - В `UnitTests/TransactionUnitTests.swift` ожидания по структуре JSON не совпадают с `Transaction.encode`.

## Проблемы среднего приоритета (P2)
- **DI/тестируемость**: `AppDependencies` жёстко создаёт реализации внутри `init`, сложно подменять сервисы.
- **Дублирование**: повторяющаяся обработка `NetworkError` и печать ошибок в нескольких ViewModel.
- **Локализация**: смешанный подход (ключи vs “сырой” текст), много строк “вшито” прямо в код.
- **UX и производительность**:
  - Некоторые ViewModel запускают “полный refresh” на действия, где достаточно локальной сортировки.
  - Fuzzy search без debounce и с тяжёлой метрикой может тормозить на больших списках.

## Рекомендуемая последовательность улучшений
1. **Потокобезопасность SwiftData**: сделать `BackupService` actor’ом или изолировать `ModelContext` через единственный serial executor.
2. **Выровнять offline‑модель**:
   - убрать wipe‑обновление транзакций;
   - добавить reconciliation для POST;
   - уточнить правила “фатальности” ошибок.
3. **Нормализовать числовые форматы**: парсить server‑числа через `Locale(identifier: "en_US_POSIX")`, а UI форматировать через текущую локаль.
4. **Свести обработку ошибок** к одному месту (Logger + UI‑политика).
5. **Подправить тесты** под фактические контракт/кодирование моделей.
